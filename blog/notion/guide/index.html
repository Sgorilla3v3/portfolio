계층 구조

노션은 Organization → Workspace → Teamspace → Page → Block 순으로 중첩되는 계층 구조를 갖는다. 이 구조를 먼저 이해해야 권한 설계와 정보 배치가 명확해진다. 상위 단계의 설정이 하위로 내려오기 때문에, 어디에 무엇을 두느냐에 따라 팀 전체의 접근 범위가 달라진다.

Organization (Enterprise 전용)
 └── Workspace — 모든 콘텐츠의 최상위
     ├── Teamspace — 팀/부서 단위 공간 (유료 플랜)
     │     └── Page
     │           ├── Block / Sub-page
     │           └── Database → Item (각 행 = 페이지)
     ├── Shared — 공유 섹션
     └── Private — 개인 섹션

Teamspace 4가지 유형

팀스페이스는 노션 워크스페이스 내 팀·부서 단위 공간이다. 각 팀스페이스는 독립적인 멤버와 권한 설정을 갖기 때문에 팀별로 접근 범위를 다르게 구성할 수 있다. 개발팀은 코드 문서와 이슈 트래킹을, 마케팅팀은 캠페인 자료를 각자의 팀스페이스에서 독립적으로 관리하는 방식이다.

유형공개 범위가입 방식활용 예시
Open전체 공개자유 참여전사 공지, 공용 자료
Closed전체 공개초대받아야 참여부서 협업
Private멤버에게만초대 전용임원진, 기밀 프로젝트
Default전체 자동 포함자동 포함온보딩 기본 공간
블록(Block) 유형 분류

노션에서 페이지에 추가되는 모든 콘텐츠는 '블록' 단위로 존재한다. 텍스트 한 줄도, 이미지 하나도, 데이터베이스 전체도 각각 하나의 블록이다. 블록은 드래그&드롭으로 자유롭게 재배치할 수 있고, 하나의 블록을 다른 유형으로 그 자리에서 변환하는 것도 가능하다.

역할 계층

노션의 권한은 '워크스페이스 역할'과 '페이지 단위 권한' 두 축으로 구성된다. 역할은 전체 워크스페이스에서의 위치를 결정하고, 페이지 권한은 개별 페이지에서의 행동 범위를 제어한다. 두 체계가 조합되기 때문에, 같은 Member라도 특정 페이지에서는 읽기만 가능하고 다른 페이지에서는 편집까지 할 수 있다.

Organization Owner (Enterprise — 전체 조직 관리)
 └── Workspace Owner — 설정·멤버·삭제 전권
     └── Membership Admin (Enterprise — 멤버 추가/제거만)
         └── Member — 유료 시트, 전체 워크스페이스 접근
             └── Guest — 무료, 초대 페이지만 접근
페이지 단위 권한 레벨

팀 협업 시 가장 흔한 실수는 모든 구성원에게 Full Access를 부여하는 것이다. Can Edit와 Can Edit Content를 구분해서 사용하면 DB 구조가 의도치 않게 변경되는 사고를 예방할 수 있다. 외부 협력사나 클라이언트에게는 Can Comment나 Can View만 부여하는 것이 원칙이다.

권한편집공유·권한변경댓글열람
Full Access✓✓✓✓
Can Edit✓—✓✓
Can Edit ContentDB 내 페이지만—✓✓
Can Comment——✓✓
Can View———✓
⚠️
주의 — Full Access 권한자는 Workspace Owner를 포함한 상위 멤버도 해당 페이지에서 제거할 수 있다. 외부인에게 Full Access를 부여하지 않도록 주의가 필요하다.
권한 상속 원칙

노션의 권한은 기본적으로 상위 페이지에서 하위 페이지로 내려온다. 상위 페이지를 공유하면 그 아래 모든 하위 페이지가 자동으로 포함된다. 단, 하위 페이지에서 개별 조정이 가능해서 특정 페이지만 접근을 막거나 다른 사람을 추가 초대하는 것도 가능하다.

1
상위 페이지에 공유하면 하위 페이지 자동 포함
2
하위 페이지에서 개별 권한 조정 가능 — 상속 차단 또는 확장
3
팀스페이스 권한 + 개별 페이지 권한 조합으로 세밀 제어
4
Permission Group으로 여러 멤버를 묶어 일괄 권한 부여

데이터베이스 뷰 7가지

Relation — 관계형 프로퍼티

Relation은 노션을 단순 메모 도구에서 실제 데이터베이스처럼 사용할 수 있게 해주는 핵심 기능이다. 두 DB를 연결하면 한쪽에서의 변경이 반대쪽에 즉시 반영되기 때문에, 정보를 중복 입력하지 않고도 여러 DB가 하나의 연결된 시스템처럼 작동한다.

↔ Two-way (양방향)
특징양쪽 DB에 Relation 프로퍼티 생성, 상호 참조
추천프로젝트 ↔ 태스크, 부모-자식 구조
→ One-way (단방향)
특징한쪽에만 프로퍼티 생성, 단순·깔끔
추천단순 참조, 자기참조(Self-Relation)
Rollup 집계 함수 전체

Rollup은 Relation으로 연결된 항목들의 데이터를 끌어다 집계한다. 프로젝트마다 연결된 태스크들의 완료율을 자동 계산하거나, 클라이언트별 총 인보이스 금액을 합산하는 식으로 활용한다. Rollup을 사용하려면 먼저 Relation이 설정되어 있어야 한다.

모든 집계 함수
함수설명타입
Show original / Show unique values원본 표시 / 중복 제거 표시전체
Count all / Count values전체 개수 / 비어있지 않은 값 개수전체
Sum / Average / Median합계 / 평균 / 중간값숫자
Min / Max / Range최솟값 / 최댓값 / 범위(Max−Min)숫자
Earliest / Latest date최초 / 최신 날짜날짜
Percent checked체크된 비율 — 진행률 추적의 핵심체크박스
고급 Rollup 실전 패턴
패턴 1: 프로젝트 진행률 자동 계산 Projects DB ← Rollup(Tasks.Checkbox) → Percent checked 패턴 2: 지출 카테고리별 합계 Categories DB ← Rollup(Expenses.Amount) → Sum 패턴 3: 직원 평균 연령 (회사별) Companies DB ← Rollup(People.Age) → Average 패턴 4: 언어 목록 중복 제거 Companies DB ← Rollup(People.Languages) → Show unique values ※ 한계: Rollup의 Rollup 직접 불가 → Formula로 우회
Formula 활용 패턴

Formula는 다른 프로퍼티 값을 참조해 자동으로 계산하거나 조건을 판단한다. 마감일 기준 D-Day 표시, 완료 여부에 따른 상태 텍스트 자동 변경, 지연 항목 자동 감지 등에 자주 쓰인다. Notion 3.0부터는 자연어로 설명하면 AI가 수식을 자동으로 생성해준다.

// D-Day 계산 dateBetween(prop("마감일"), now(), "days") // 진행 상태 텍스트 if(prop("완료") == true, "✓ 완료", "진행중") // 지연 여부 자동 판단 if(prop("마감일") < now() and prop("완료") == false, "지연", "정상")
✨
Notion 3.0~ 자연어 설명 → AI가 Formula 자동 생성. 복잡한 조건문도 한국어로 구현 가능.

기존 AI vs Personal Agent

Personal Agent는 이전 Notion AI와 근본적으로 다르다. 기존 AI가 현재 페이지 안에서 '제안'만 했다면, Personal Agent는 요청 한 번으로 워크스페이스 전체를 탐색하고 직접 실행까지 한다. 프로젝트 계획 수립부터 태스크 분해, 담당자 지정, 문서 초안 작성까지를 한 번의 지시로 연속 처리한다.

지시서(Instruction Page) 작성 예시

에이전트의 성능은 Instruction Page 품질에 크게 좌우된다. 자주 참조할 DB 링크, 선호하는 응답 형식, 회사 전용 용어 등을 구체적으로 작성할수록 더 정확하고 일관된 결과물을 얻을 수 있다. Instruction Page는 일반 노션 페이지이기 때문에 언제든 수정하고 개선할 수 있다.

## 역할 업무 보조 에이전트 — 보고서 작성 및 데이터 정리 전담. ## 응답 형식 - 보고서: 표 형식 + 3줄 요약 - 태스크 목록: 담당자 멘션(@) 포함 - 수치 데이터: 항상 단위 명시 ## 자주 참조할 DB - 프로젝트 현황: [링크] - 주간 리포트 템플릿: [링크] - 팀원 목록: [링크] ## 주의 사항 - 외부 공개 링크 생성 금지 - 민감 정보 포함 DB 접근 전 확인 요청

Personal Agent vs Custom Agent

Custom Agent는 사람이 요청하지 않아도 스스로 작동한다는 점에서 Personal Agent와 근본적으로 다르다. 스케줄이나 특정 이벤트를 트리거로 설정해두면 24시간 지정된 작업을 자율적으로 처리한다. Personal Agent가 "요청할 때 움직이는 조수"라면, Custom Agent는 "알아서 일을 처리하는 전담 팀원"에 가깝다.

5가지 구성 요소

Custom Agent 하나는 다섯 가지 요소로 구성된다. 트리거가 발동 조건을 결정하고, 지시서가 행동 방식을 정의하며, 소스가 접근 가능한 데이터 범위를 제한한다. 모든 요소는 자연어로 설정할 수 있으며, Notion AI가 입력 내용을 바탕으로 자동 구성해준다.

주요 활용 패턴

실제 팀에서 Custom Agent를 도입할 때 가장 효과적인 시작점은 반복 응답 업무다. Slack에서 매일 같은 질문을 받는 IT·HR 채널이나, 정해진 형식의 주간 보고서 발송처럼 규칙이 명확한 작업부터 적용하면 빠르게 효과를 확인할 수 있다. 규칙이 명확할수록 에이전트가 정확하게 동작한다.

AI 도입 단계별 권장 순서

팀에서 노션 AI를 도입할 때 가장 흔한 실패는 Custom Agent부터 시작하는 것이다. 워크스페이스 데이터 구조가 정리되지 않은 상태에서 에이전트를 붙이면 잘못된 결과물만 빠르게 만들어낸다. 데이터 구조를 먼저 정리하고, 단계별로 점진적으로 확장하는 것이 핵심이다.

1

즉시 활용 가능

AI 요약·글쓰기 보조 / AI 미팅 노트 / DB Autofill

2

워크스페이스 정비 후

Personal Agent 지시서 작성 → 반복 리포트 자동화

3

팀 단위 확장

Enterprise Search 세팅 / Custom Agent 1~2개 시범 운영 (Q&A봇, 리포트봇)

4

스케일업

Custom Agent 역할별 전문화 / MCP 연동으로 외부 도구와 통합 워크플로우
